# Document Objective

This document establishes the **coding standards, naming conventions, architectural rules, documentation requirements, and engineering best practices** that every module in this project must follow.

These rules are mandatory for:

- Manual development
- AI-generated code
- Future maintenance
- Code reviews
- Assignment submission

The goal is to ensure the project looks like it was written by **one experienced Android engineer**.

---

# 1. Engineering Principles

Every implementation must follow:

- SOLID Principles
- Clean Architecture
- Repository Pattern
- MVI
- Immutable State
- Composition over Inheritance
- Single Responsibility
- Dependency Inversion
- Offline-first Architecture

Never compromise architecture for convenience.

---

# 2. General Coding Rules

Always

- Write readable code.
- Prefer clarity over cleverness.
- Keep functions small.
- Keep classes focused.
- Use immutable data.
- Fail safely.

Never

- Duplicate logic.
- Use magic numbers.
- Use hardcoded strings.
- Ignore exceptions.
- Leave TODOs in completed features.
- Commit commented-out code.

---

# 3. Kotlin Style Guide

Follow the official Kotlin Coding Conventions.

Use

```kotlin
val
```

by default.

Use

```kotlin
var
```

only when mutation is genuinely required.

Prefer expression bodies for simple functions.

Avoid unnecessary `!!`.

Prefer

```kotlin
?.let { }
?: 
require()
check()
```

over force unwrapping.

# 8. Function Naming

Use verb-based names.

Good

```text
loadScreen()

updateComponent()

validateJson()

saveScreen()
```

Avoid

```text
screen()

component()

json()
```

---

# 9. Variable Naming

Good

```text

selectedComponent

isLoading

isValid

rendererState
```

Avoid

```text

temp

```

Names should express intent.

---

# 10. Constants

Never inline repeated values.

Create

```text
Constants.kt

JsonConstants.kt

NavigationConstants.kt
```

Use

```kotlin
const val
```

where appropriate.

---

# 11. Compose Guidelines

Composable functions must

- Be stateless whenever possible.
- Hoist state.
- Accept immutable models.
- Use Material 3.
- Remain previewable.

Never

- Access Repository.
- Launch business logic.
- Parse JSON.
- Hold long-lived mutable state.

---

# 12. ViewModel Guidelines

ViewModels

May

- Dispatch intents
- Execute UseCases
- Emit State
- Emit Events

Never

- Access DAO
- Parse JSON
- Navigate directly
- Know Room implementation

---

# 13. Reducer Guidelines

Reducer must be

- Pure
- Deterministic
- Stateless

Never

- Launch coroutines
- Access Repository
- Emit events
- Modify mutable state

---

# 14. Repository Guidelines

Repositories

May

- Coordinate data
- Validate
- Map
- Execute transactions

Never

- Return Room entities
- Know Compose
- Know Navigation

---

# 15. UseCase Guidelines

Every UseCase

- One responsibility
- Small constructor
- No Android dependency
- No Room dependency

Examples

```text
LoadHomeUseCase

SaveComponentUseCase

SeedDatabaseUseCase
```

---

# 16. Entity Guidelines

Room Entities

- Data only
- No business logic
- No Compose
- No validation

Mapping happens outside entities.

---

# 17. Mapper Guidelines

Mapper responsibilities

Only

```text
Entity

↓

Domain

↓

UI
```

No validation.

No repository calls.

---

# 18. Validator Guidelines

Validators

Must

- Return validation results
- Never throw for expected validation failures
- Be reusable
- Be stateless

---

# 19. JSON Guidelines

Always

- Validate before saving
- Pretty print in debug builds
- Preserve ordering
- Preserve IDs

Never

- Modify payload silently
- Ignore schema version

---

# 20. Error Handling Rules

Never expose

- Stack traces
- SQL errors
- Serialization exceptions

Convert all errors to domain failures.

Use centralized logging.

---

# 21. Logging Standards

Format

```text
[Module][Level] Message
```

Examples

```text
[Renderer][INFO]

Rendering Home
```

```text
[Validator][WARNING]

Unknown Widget
```

Release builds minimize logging.

---

# 22. Coroutine Rules

Use

- Structured concurrency
- CoroutineScope owned by ViewModel
- Injected dispatchers

Never

- GlobalScope
- Blocking calls on Main
- Nested launches without purpose

---

# 23. Flow Guidelines

Read

↓

Flow

Write

↓

Suspend

State

↓

StateFlow

Events

↓

SharedFlow

Never use LiveData.

---

# 24. Documentation Standards

Every public class should include KDoc.

Document

- Purpose
- Parameters
- Return value
- Exceptions (if any)

Avoid redundant comments.

---

# 25. Testing Standards

Every new feature requires

- Unit tests
- Integration tests (where applicable)
- UI tests for critical flows

Tests must be deterministic.

---

# 26. Compose Preview Standards

Every screen should provide previews for

- Loading
- Success
- Error
- Empty

Widgets should also include previews where practical.

---

# 27. Dependency Injection Standards

Always

- Constructor injection
- Interface bindings
- Scoped dependencies
- Inject dispatchers

Never

- Manual object creation
- Service locator
- Singleton business objects

---

# 28. Git Commit Standards

Format

```text
type(scope): description
```

Examples

```text
feat(home): add SDUI renderer

fix(database): handle migration failure

test(renderer): add fallback tests

docs: update architecture
```

Types

- feat
- fix
- refactor
- docs
- test
- chore
- build
